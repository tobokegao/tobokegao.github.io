# 0048 メモの検索の索引は、ポストを1日ごとのページにして作る

- **日付**: 2026-11-18
- **決めたこと**: メモの検索の索引（Pagefind）に入れるポストを、月ごとのページではなく、1日ごとの小さなページにする。Pagefindは1.3.0から1.6.0に上げる。
  - 1日ごとのページは、組み立てのあとに`scripts/memo_search_pages.py`が月のページから切り出す（`public/memo/_d/`）。索引を作ったら消すので、公開されない。
  - 月のページとリポストの月のページは、索引に入れない。話題のページは、名前とノートの本文だけを入れる（ポストの一覧は入れない）。
  - 1日ごとのページには、月（`m`）とリポストかどうか（`rt`）、絞り込みの`month`と`kind`（`own`か`rt`）を付ける。話題のページの`kind`は`topic`。
  - 検索の結果は1日（または話題）が1件。10件ずつ出し、残りは「もっと見る」で出す。リンクは月のページの、そのポストの位置に向ける。
  - `since:`や`from:`などで絞るときは、Pagefindの絞り込み（`kind`と`month`）で先にページを減らし、そのあとポストを1つずつ確かめる。見るのは上位300日まで。
- **理由**:
  - 検索が重かった（2026-11-17）。Pagefindは、当たったページごとに、ページの全文から抜粋をブラウザで作る。月や話題のページは1ページにポストが数百件あり（大きいものは本文34万字）、上位20ページの抜粋づくりに0.5〜1秒かかった。その間は入力欄も固まった。通信も1回の検索で0.5〜1.8MBあった。
  - 1日ごとにすると、20ページ分の抜粋づくりが9〜15ミリ秒になり、通信はおよそ15分の1になった（手元で計測）。
  - ポスト1件ごとにする案はやめた。ページが約32万個になり、索引を作るのに手元で12分かかった。公開の処理は10分で打ち切られる。初回に読むファイルも42KBから2MBに増えた。
  - 1日ごとのページをHugoに作らせる案もやめた。月のページのHTMLをそのまま切り出せば、ポストの見た目の決まり（`notes-post.html`）が1か所のままになり、検索とミニとぼけがおが読む形も変わらない。
  - Pagefind 1.3.0は、1日ごとの索引で「ライブ」を探すと中で止まった（`RuntimeError: unreachable`）。1.6.0では止まらない。
  - 1.6.0はカタカナの語を途中で切らない。1日ごとの索引で比べると、「チップチューン」は70日から3,498日、「セットリスト」は1日から541日、「ゲームボーイ」は13日から1,495日に増えた。1.3.0では取りこぼしていた。
  - 容量は、メモのページ約440MBに索引約135MBで、合わせて約580MB。GitHub Pagesの上限（1GB）に収まる（0022）。索引のファイルは約1万5千個。
- **守り方**:
  - 索引を作る順番は、`memo_search_pages.py public` → `pagefind --site public` → `memo_search_pages.py public --clean`（`build.yml`）。消し忘れると、1日ごとのページが公開される。
  - `memo_search_pages.py`は、月のページから拾ったポストの数が`data/memo/graph.json`と合わないと止まる。ポストのHTML（`notes-post.html`の`article.np`と`time`）を変えたら、ここも確かめる。
  - 手元で試すときは、Pagefindの配布物（`~/tools/pagefind-1.6.0`）で同じ順番に動かす。同じフォルダに索引を作り直すと古いファイルが残るので、大きさを測るときは新しいフォルダに作る。
  - ミニとぼけがお（0032、0045、0046）は同じ索引を使う。Pagefindのバージョンを上げたら、検索とあわせて答えも試す（0038）。
